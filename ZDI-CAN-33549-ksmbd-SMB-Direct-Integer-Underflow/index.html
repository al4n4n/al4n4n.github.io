ZDI-CAN-33549: ksmbd SMB Direct Integer Underflow, 8 Bytes to Kernel Crash

Posted on 2026-10-24
ZDI-CAN-33549 CVSS 9.0: a one-line integer underflow in Linux ksmbd's SMB Direct RDMA handler lets an authenticated attacker write 8KB past an 8-byte kernel heap allocation. Full PoC over RDMA with KASAN proof and 0x4141414141414141 in kernel registers.

Every Linux machine running ksmbd with SMB Direct is one crafted SMB2 WRITE away from a kernel crash. One line of code, an 8-byte heap allocation, and a size_t that wraps to 0xFFFFFFFFFFFFFFFF.

I built a full SMB Direct client from scratch (RDMA connection management, SMB2 session negotiation, NTLMv2 authentication, the whole stack) to trigger a single integer underflow deep inside the kernel’s RDMA descriptor processing. The result: KASAN reports a slab-out-of-bounds write of 1024 bytes past an 8-byte kmalloc. Then the kernel follows a pointer full of my 0x41 bytes and hits a general protection fault.

ZDI-CAN-33549. CVSS 9.0. Fixed in commit 5b8ce2e. PoC, check script, detection rules: github.com/al4n4n/ZDI-CAN-33549.

Background: what ksmbd is and why it matters

ksmbd is an in-kernel SMB/CIFS server that landed in Linux 5.15 as a high-performance alternative to Samba. Unlike Samba, which runs as a userspace daemon with its own address space, ksmbd handles SMB requests directly in kernel context. Every ksmbd bug is a kernel bug: there’s no sandboxing, no ASLR at the process level, no graceful crash recovery. When ksmbd crashes, the whole machine goes down.

SMB Direct (SMB over RDMA) is the fast path. Instead of copying data through TCP socket buffers, the client and server register RDMA memory regions and do direct DMA reads and writes into each other’s memory. This is how enterprise NAS appliances and high-performance storage clusters move data at wire speed. The trade-off: the kernel trusts the client’s RDMA scatter/gather descriptors to stay within the allocated buffer. When they don’t, the DMA engine writes directly into whatever sits next to the buffer in the SLAB allocator.

Any deployment running ksmbd with CONFIG_SMB_SERVER_SMBDIRECT enabled and an RDMA-capable network (InfiniBand, RoCE, iWARP, or even the software emulator soft-RoCE) is exposed. The attacker needs to authenticate to any share (NTLMv2 with valid credentials is sufficient, and in many environments default or test accounts exist), but after that a single SMB2 WRITE request triggers the bug.

The vulnerable code

The function smbdirect_connection_rdma_xmit() in fs/smb/smbdirect/rw.c processes a list of RDMA descriptors from the client. Each descriptor says “read/write N bytes at offset M into the buffer.” The server iterates the list, subtracting each descriptor’s length from buf_len, which tracks how many bytes of buffer space remain.

The intent is straightforward: if a descriptor exceeds the remaining buffer, clamp it and stop. Here’s what happens instead:

Let me trace it step by step for our trigger values (buf_len = 8, desc[0].length = 4096):

  1. desc_buf_len (4096) > buf_len (8): the descriptor exceeds the buffer
  2. desc_buf_len = buf_len → desc_buf_len = 8: clamp to remaining space
  3. buf_len = 0: mark buffer as consumed
  4. buf_len -= desc_buf_len → 0 - 8: unsigned underflow

Since buf_len is a size_t (unsigned 64-bit), 0 - 8 wraps to 0xFFFFFFFFFFFFFFF8. Now buf_len is effectively infinite. The loop continues to the next descriptor. The if (!buf_len) break; check at the top of the loop passes (because SIZE_MAX is very much nonzero) and the second descriptor’s full length is accepted without any bounds check.

The fix is to delete the buf_len = 0; line. Without it, after clamping desc_buf_len = buf_len, the subtraction buf_len -= desc_buf_len naturally produces 0. The loop breaks on the next iteration via the existing if (!buf_len) break; check. One line removed. That’s the whole fix.

Walking the exploit: from underflow to kernel crash

Here’s what happens inside the kernel when the exploit fires. This is the part that matters: the mechanism that turns a one-line off-by-one in buffer tracking into attacker-controlled heap corruption.

Step 1: The allocation. When ksmbd receives an SMB2 WRITE with RemainingBytes=8, it calls kvmalloc(8) inside smb2_write(). The SLAB allocator hands back an 8-byte object from the kmalloc-8 cache. This is a tightly packed cache: objects are back-to-back in memory, separated by nothing but the SLAB allocator’s internal metadata and other live objects.

Step 2: The first descriptor. Our desc[0].length = 4096 triggers the clamping path. The code clamps it to 8 bytes (the buffer size), registers the RDMA region for those 8 bytes, and then the underflow fires. buf_len wraps to SIZE_MAX.

Step 3: The second descriptor. With buf_len at SIZE_MAX, our desc[1].length = 8192 passes all checks. The kernel registers an 8192-byte RDMA region starting at the base of our 8-byte buffer.

Step 4: The DMA write. The soft-RoCE driver (rxe) executes the RDMA operation. rxe_mr_copy() does a memcpy of 8192 bytes into an 8-byte buffer. The first 8 bytes land in the allocated object. The remaining 8184 bytes overwrite whatever sits next to it in the kmalloc-8 SLAB page: other kernel objects, their function pointers, their internal linked lists.

Step 5: The corruption spreads. Our write payload is filled with 0x41 bytes. These overwrite the next pointers of adjacent SLAB objects. When ksmbd later tries to tear down the SMB Direct connection, it calls smbdirect_connection_destroy_mem_pools(), which walks the SLAB free list. It dereferences a pointer that now contains 0x4141414141414141. The kernel tries to access that non-canonical address and hits a general protection fault.

This is the critical insight: the attacker fully controls the content being DMA’d into the heap. In this PoC, I used 0x41 bytes to make the corruption visible in register dumps. A real exploit would place a crafted structure here (a fake kmem_cache descriptor, a corrupted sk_buff, or a function pointer overwrite) to turn the heap corruption into controlled code execution. I didn’t build that part, because demonstrating the mechanism is the point. The jump from “attacker controls 8KB of kernel heap” to “attacker controls RIP” is an engineering exercise, not a research question.

The trigger

The PoC, s3rig.c, implements a complete SMB Direct client over RDMA from scratch: rdma_cm for connection management, ibverbs for RDMA operations, and a full NTLMv2 authentication stack. The exploit path:

  1. RDMA connect to ksmbd (port 445)
  2. SMB Direct negotiation (version 0x0100)
  3. SMB2 NEGOTIATE (dialect 3.0.2)
  4. SMB2 SESSION_SETUP with NTLMv2 challenge-response
  5. SMB2 TREE_CONNECT to a share
  6. SMB2 CREATE to open a file
  7. SMB2 WRITE with RemainingBytes=8 and two RDMA descriptors:
    • desc[0].length = 4096 → triggers the clamp + underflow
    • desc[1].length = 8192 → writes 8KB OOB past the 8-byte buffer

The WRITE tells ksmbd: “I have 8 bytes of data to write, here are the RDMA regions where it lives.” ksmbd allocates 8 bytes, and the underflow lets the second descriptor DMA 8192 bytes directly past the end of that allocation.

Building the lab

This isn’t a trivial bug to reproduce. You need a kernel built with ksmbd, SMB Direct, soft-RoCE (the software RDMA emulator), and KASAN, all compiled in, not as modules. I used a QEMU VM running Linux 7.3-rc3 (the last vulnerable version) with a Debian Trixie rootfs:

Inside the VM: create a soft-RoCE device over eth0, configure ksmbd with a test share and user, and build s3rig. The repo includes setup.sh to automate all of this.

One gotcha that cost me hours of debugging: OpenSSL 3.x in Debian Trixie doesn’t load the legacy provider by default. EVP_md4() silently returns NULL, which means the MD4 hash at the core of NTLMv2 produces garbage. Every authentication attempt failed with STATUS_LOGON_FAILURE (0xc000006d). I wrote a standalone test program that computed NT hashes with and without the legacy provider, compared against known-good values, and confirmed the root cause. Who’s affected: Any Linux machine running ksmbd with SMB Direct enabled and an RDMA-capable network. This includes enterprise NAS appliances, high-performance storage clusters, and cloud RDMA deployments where containers share a ksmbd-enabled host kernel. The attacker needs any authenticated session: a test account, a guest share, anything that gets past NTLMv2.

Detection

The repo includes Suricata and Sigma rules.

  • Network (Suricata): Detects SMB2 WRITE with suspiciously small RemainingBytes. Note that SMB Direct traffic may bypass network IDS entirely on native RDMA fabrics; this rule works best on soft-RoCE or when traffic is mirrored.
  • Host (Sigma): Matches BUG: KASAN: slab-out-of-bounds and general protection fault patterns in kernel logs, anchored to ksmbd and rxe stack frames.

Best mitigation: update the kernel. The fix is in mainline as commit 5b8ce2e.

Fix

Namjae Jeon’s fix removes the buf_len = 0; line. Without it, after clamping desc_buf_len = buf_len, the subtraction buf_len -= desc_buf_len naturally produces 0. The loop breaks on the next iteration via the existing if (!buf_len) break; check.

The fix patches the introduction commit e628bf939aaf. Affected: all kernels from that commit through 7.3-rc3. Fixed: 7.3-rc3+ with the patch applied, and any backport that removes the buf_len = 0; line.
